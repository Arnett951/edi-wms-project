# bip-report: rules for the CR pipeline (and any AI implementer)

This service runs on **Skynet** (home lab Docker, tailnet only). Nothing here is deployed by
GitHub Actions, and the pipeline has no access to Skynet or to its Db2 database. Merging a
branch does **not** put a report live. A human copies the files to Skynet after merge.

## What a "new report" CR should produce

A new folder `bip-report/reports/<report-id>/` (id: lowercase letters, digits, `-`) containing:

1. `report.json`: same shape as the existing reports (see README "Adding a report"). Pick an
   `order` that doesn't collide with the other folders.
2. `dataset.sql`: **one SELECT** against Db2 LUW schema `WMS` (database `TIREWMS`):
   - `:P_FACILITY` wherever the warehouse code goes; it's the only parameter supported.
   - End with `WITH UR`.
   - Upper-case column aliases; they become the XML element names the template uses.
   - Db2 syntax, not T-SQL (`FETCH FIRST n ROWS ONLY`, `CURRENT DATE`, `DAYS()`, `VARCHAR_FORMAT`).
   - No quotes inside `--` comments, no text after `;` on a line (Db2 CLP gotchas).
3. `template.rtf`: generated by a new `tools/build_<report>_template.py`, following
   `tools/build_scorecard_template.py` / `build_heatmap_template.py`. Hand-written RTF is
   fine too, but the generator pattern is what the repo already uses. Obey the RTF parser
   lessons in README.md (`{\info}` group, `{}` formatting groups, `if@inlines` mid-line).
4. `sample.xml`: a few hand-written `<DATA><DATA_RECORD>...` rows matching the SQL's column
   aliases, so a human can open the template in Template Builder for Word before deploying.

The Operational Reporting page lists reports from the Skynet registry at runtime. **No
dashboard (`dashboard/`) or API (`api/`) change is needed for a new report**, so don't make one.

## Where the schema lives

You can't query Db2. Use these as the column reference, and only use columns you can find in them:

- `reports/*/dataset.sql`: the working queries (WAREHOUSE, ITEM, INVENTORY, LOCATION, LOT_ATTRIBUTE,
  INVENTORY_TRANSACTION, OUTBOUND_ORDER, OUTBOUND_LINE, SHIPMENT, SHIP_TO, CARRIER).
- `sql/lab/*.sql`: DDL for the tables added later (rack grid, carrier/ship-to/shipment, history).

The API's `list_schema_columns` intake tool reads **Azure SQL**, not Db2. A "table not found"
there says nothing about `WMS.*`.

If a request needs a column or table that doesn't appear in those files, stop and say so
in the final message rather than inventing one.

## Never do this

- Don't try to deploy: no `ssh`, `scp`, `docker`, or Tailscale. There is no Skynet access.
- Don't change `src/BipReportServer.java`, the `Dockerfile`, or `config/` for a report CR. Those
  need a container rebuild on Skynet, so they're out of scope for the automated pipeline.
- Don't add DDL/DML under `sql/lab/` for a report CR. Lab data changes are manual.
- Don't edit another report's folder unless the CR is about that report.

## Final message: include the manual deploy steps

End with this block (fill in the id) so the human reviewer can deploy after merge:

```
MANUAL DEPLOY (after merge; the pipeline can't reach Skynet):
  scp -r bip-report/reports/<report-id> skynet:~/bip-report/reports/
  ssh skynet 'docker logs bip-report 2>&1 | grep -E "SEVERE|compiled|skipping"'
  Then pick the report on https://www.edi.chrisarnett.me/?tab=bi-publisher and render one facility.
  Unverified: the SQL never ran against Db2 and the RTF never compiled with the BIP engine.
```
